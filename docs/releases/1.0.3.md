# 1.0.3：作者投稿回执与诗稿排版修复

本版修复作者调用 `ephemera_publish` 时，稿件格式或版式问题被报告为 MCP 错误、具体拒稿原因丢失，以及诗稿长句可能侵入落款区的问题。作者能在同一次投稿结果中看到“已出版”“拒稿及修改意见”或明确的服务状态。

## 1. 投稿失败为什么曾经变成 MCP 错误

此前有两条路径会让可修正的稿件问题进入工具错误通道：

1. MCP SDK 在作者处理函数之前执行严格输入校验。例如把 `manuscript` 传成转义后的 JSON 字符串时，SDK 直接返回输入校验错误，作者处理函数没有机会生成正常拒稿回执。
2. 体裁与版式不匹配等业务异常被包装为 `isError: true` 的工具结果。某些宿主因此显示 MCP error，而不是一份说明如何修稿的出版回执。

受理后的拒稿还有另一处信息丢失：部分永久渲染失败只保存错误代码，没有保存具体原因，最终只能返回笼统的“稿件未通过检查”。

### 现在的行为

工具发现仍公布严格的稿件 schema，服务仍按该 schema 校验。可修正的输入问题由作者处理函数接收并转换为正常业务回执，不跳过稿件校验，也不把失败算作出版成功。

| 情况 | 之前 | 1.0.3 |
| --- | --- | --- |
| `manuscript` 是字符串，或字段类型不正确 | 可能在 SDK 层成为工具错误 | 返回 `rejected`，指出字段及正确填写方法 |
| `content.kind` 与 `layoutVariant` 冲突 | 业务错误进入 MCP 错误通道 | 指出体裁与版式冲突，并给出修改参数的建议 |
| 所选版式没有作者填写的栏目 | 错误信息不一定指出如何保留内容 | 指出栏目；建议使用能承载该栏目的体裁，避免丢弃原文 |
| 受理后的内容或排版拒稿 | 部分结果只有错误代码或通用文案 | 保存具体反馈，在最终回执和状态查询中使用 |
| 排版审核拒绝 | 具体审核意见可能被通用错误掩盖 | 保留已有 `returnFeedback`，不替换为笼统拒稿理由 |

正常作者回执的 `status` 包括：

- `published`：作品已经提交出版，带作品信息。它不表示墨水屏已经显示。
- `rejected`：本次未出版，带 `issues`。每项包含 `field`、`message` 和 `suggestion`；审核意见可指向整页。
- `unavailable`：服务暂时无法完成本次出版，不需要修改稿件。
- `unconfirmed`：暂时无法确认出版结果。不要把它当作确定失败后立即重复投稿，应先核对已有作品或由管理员确认。

这些是正常 MCP 结果中的业务状态，不以 `isError: true` 表达。连接中断、协议或鉴权失败仍可能由 MCP 或宿主报告为技术错误，本版不承诺将所有外部故障转换成业务回执。

以下是拒稿业务内容的示例，说明回执结构，具体文字取决于实际问题：

```json
{
  "status": "rejected",
  "message": "本次未出版：稿件体裁与指定版式不一致。",
  "issues": [
    {
      "field": "manuscript.layoutVariant",
      "message": "content.kind=note 与 layoutVariant=poem-portrait 不匹配。",
      "suggestion": "若本意是诗稿，请使用 content.kind=poem 并填写 content.text；若要保留便签体裁，可省略 layoutVariant 自动选版。"
    }
  ]
}
```

技术故障不会被当作作者内容有问题。服务、模型或存储暂时不可用时，不要求作者删字、改写或调试连接。内部路径、堆栈和排版测量数据不进入作者修改意见。本版也没有降低审核要求、关闭审核或将审核否决改为成功。

## 2. 诗稿改用一个 `content.text` 字符串

新投稿将整首诗放入 `content.text`，用换行符表示诗行。JSON 中的 `\n` 解码后就是换行，不需要给模型提供字符串数组，也不要把整个 `manuscript` 再转义成字符串。

可直接作为 `ephemera_publish` 参数的示例：

```json
{
  "manuscript": {
    "schemaVersion": 3,
    "intent": "note",
    "content": {
      "kind": "poem",
      "text": "雨停在窗外\n\n灯还亮着\n等一阵晚风"
    },
    "layoutVariant": "poem-portrait"
  }
}
```

`layoutVariant` 可以省略，也可以明确选择当前启用的诗版式，例如 `poem-portrait` 或 `poem-landscape`。结构诗稿不需要再复制一份 `body`，也不要同时提交 `text` 和 `lines`。

原始字符串中的 LF、CRLF、空行及行序会保存在稿件中，正文投影和作品回读保留原文。排版时才把换行拆成诗行；空行保留为列间的空白位置。下面两种写法各自保留自己的换行形式：

```json
{ "kind": "poem", "text": "第一句\n\n第二句" }
```

```json
{ "kind": "poem", "text": "第一句\r\n\r\n第二句" }
```

### 实际排版决定句子能否放下

字符串能通过输入校验，不代表每一句都能放进当前纸面。此前仅看整页越界时，横版诗的文字可能已经进入落款区，却仍在页面范围内。

本版使用 Chromium 中的实际文字范围，检查诗句是否超出诗稿可用区域、侵入落款区，以及诗行列数是否超出横向空间。过长单句以 `render_overflow` 结束本次出版，并在正常拒稿回执中指出行号，例如“诗稿第 1 行的句长超出当前版式的可用区域”，建议作者在合适位置换行或选择可容纳该句的版式。

服务不会替作者自动断句、缩小字号、截断或删除正文。验收中使用的特定字数只是边界用例，不能作为所有字体、字符、诗行或版式通用的容量保证。

## 3. 旧客户端和历史诗稿

升级后请让 MCP 客户端刷新工具定义；若客户端缓存 schema，可断开后重新连接 MCP，再重新取得工具列表。服务重启不会自动使所有宿主缓存失效。自建调用方还应允许新的回执状态，不能继续假设所有正常结果都是 `published`。

新投稿不再使用：

```json
{ "kind": "poem", "lines": ["雨停在窗外", "灯还亮着"] }
```

应改为：

```json
{ "kind": "poem", "text": "雨停在窗外\n灯还亮着" }
```

转换新请求时按原数组顺序连接诗行，不改句子内容。仍提交 `content.lines` 的作者客户端会收到正常拒稿意见，提示迁移到 `content.text`。

已经保存的旧 `lines` 稿件和排队任务继续由内部兼容读取器处理；历史作品可以校验、排版和回看。旧数组的原有投影保留，不通过改写数据库或重新生成历史稿件完成迁移。新的作者 schema 与内部历史读取 schema 分开，历史兼容不意味着新工具仍要求提交数组。

## 4. 升级方式与范围

本次是服务端修复，不变更数据库结构、设备通道协议或设备固件。已有设备无需重新刷写或重新配对，历史稿件和设备数据不需要清空。

继续沿用公开包的 `ephemera-private` 方式：

1. 停止旧服务，按现有流程备份私人配置和数据。
2. 将完整 1.0.3 安装包解压为新目录，与原 `ephemera-private` 保持同级。不要把新包叠加覆盖成一个混合版本目录，也不要删除私人目录。
3. 在新目录使用原来的 `scripts/start-public.ps1` 启动方式。脚本发现已有 `ephemera-private/config.json` 后沿用原配置、数据、密钥和浏览器缓存；不要同时启动新旧服务访问同一数据目录。
4. 刷新作者 MCP 工具定义，检查控制台和作品回读，再开始新投稿。源码部署继续使用原私人配置和数据目录。

Node.js 要求与 **1.0.2 安全更新保持一致**：`^24.22.1 || >=26.12.1`，即 24.22.1 或更新的 24.x，或 26.12.1 及以上正式版。安装包不附带 Node.js；旧 Node 24、Node 25、早期 Node 26 及预发布版本仍不能绕过启动检查。升级 Node 后应重启实际承载服务的终端或进程管理器，并用 `node --version` 核实该进程使用的版本。

## 5. 源码验证与版本标识

公开源码增加 `npm test` 入口：测试启动器自动创建临时数据目录，结束后清理，不要求使用者手动设置测试数据库目录。需要先安装依赖、编译，并安装实际排版使用的锁定 Chromium：

```bash
npm ci
npm run build
npx playwright-core install chromium
npm test
```

如果已有锁定版本的 Chromium 缓存，可以沿用配置好的 `PLAYWRIGHT_BROWSERS_PATH`。真实排版测试需要该浏览器和随仓库提供的字体资源，不能只用 schema 校验代替。

本版同时纠正服务内报告版本与安装包版本不同步的问题：版本标识统一为 `1.0.3`，并增加一致性断言，便于核对实际运行的服务。

## 6. 验证范围

公开源码在 Windows x64、Node.js 24.22.1 和锁定 Chromium 上通过编译及 45 项回归验证，覆盖：

- 作者 MCP 输入错误、体裁与版式冲突、正常拒稿回执及技术状态区分。
- 具体拒稿原因持久化、重启与重放、排版审核反馈保留。
- 诗稿字符串 schema、LF/CRLF/空行保留、历史 `lines` 兼容及作品回读。
- 真实竖版、横版诗稿排版，长句溢出和横版落款区边界。
- 既有终态投稿、受理前拒稿与重放、排版工选版和补写边界，以及 Node 安全门槛和版本一致性。

发布包通过现有打包器从干净的 Git 提交生成；`release-manifest.json` 记录该提交、版本、运行时要求及逐文件 SHA-256。附件的启动、投稿和文件清单复验结果记录在 [v1.0.3 Release](https://github.com/IrisNyx/MoonE-ink/releases/tag/v1.0.3) 中。

这些服务端测试不代替真实墨水屏显示、外部设备连通性或长期运行验收，也不扩大已有平台和板型支持范围。安装与硬件限制继续以 [README](../../README.md) 和 [公开包快速开始](../../QUICKSTART_PUBLIC.md) 为准。
